# H．踩坑记录与改进建议

[返回总目录](../README.md)

## H.1 最需要先承认的问题

本次过程持续较长，重复兼容修复、部署和人工验证占用了大量时间。已有密钥意味着最关键的密码材料条件已具备；后续很多停顿来自恢复程序的工程设计和运行环境适配，而不是每次都遇到了新的密码学难题。

不能将反复失败全部解释为“安全所以慢”。更好的做法是区分会直接破坏数据的条件、只需要记录的兼容差异，以及会自然消失的运行时观察竞态，为它们分别设计处理路径。

## H.2 数据与空间方面

| 踩坑 | 为什么容易误判 | 应对方法 |
| --- | --- | --- |
| 看到空闲下降，就认为是回收站没清 | 独立明文分配、在途副本、打开引用、快照和共享块都能影响空间 | 同时看逻辑大小、实际分配、共享/独占度量和关闭文件后的可用空间；先诊断再决定删除 |
| 认为删除一个文件就会立即释放同样大小 | 逻辑长度不是独占字节；事务提交和仍存引用会延迟回收 | 记录删除、同步、关闭句柄和随后采样；避免根据单次卷级变化强行归因 |
| 明文与密文每一段都普通复制 | 大量原本未加密的数据也重新分配，占用高峰被放大 | 在支持的策略下使用共享候选，仅改写必要范围；不支持时使用有预算的回退或保留 |
| 承诺“绝不增加任何空间” | CoW、块对齐、日志和元数据都需要空间 | 给出空间预算、余量和停止条件，承诺可观测控制而不是数学上不可能的零写入 |
| 想靠改一个属性恢复旧共享布局 | 属性兼容、块共享和内容正确是三件事 | 空候选先适配属性；有可验证供体时才考虑重建；用实际共享度量验收 |
| 无密文的文件也套用密文恢复分支 | 失去了原密文作为校验来源 | 要求独立历史证据和合适供体，或明确只保留现有文件，不能伪造恢复证明 |

## H.3 校验与内容判断方面

| 踩坑 | 后果 | 改进 |
| --- | --- | --- |
| 把文件头正常当作全文件恢复正确 | 后续内容可能截断、损坏或使用了错误区间 | 检查完整流、大小、EOF、尾部和区间；再结合可信原件或结构验证 |
| 把加解密往返成功当作历史原文证明 | 可逆变换在错误密钥下也可能往返一致 | 记录它证明的具体一致性；另找独立来源的原文见证 |
| 用名称或大小判断哪个同名副本正确 | 可能覆盖较新编辑或完整旧版本 | 全量比较，并明确内容来源政策；差异项先保留或取得指定取舍授权 |
| 属性恢复失败就一律阻止内容恢复 | ACL、访问时间和厂商扩展等差异可长时间阻塞数据可用性 | 在明确授权的内容优先模式中记录属性差异；完整内容与身份校验继续保留 |
| 内容优先被误写成属性完全恢复 | 后续账号访问、应用权限可能出错 | 把内容结果、权限结果和存储属性结果分开验收 |
| 散列写入了日志，就认为日志证明原始真实性 | 摘要只能绑定当时读取的字节 | 记录摘要来源、生成阶段和是否来自独立可信历史证据 |

## H.4 运行时与部署方面

| 踩坑 | 本案体现 | 改进 |
| --- | --- | --- |
| 上传了外层目录或上传到了错误位置 | 短启动命令找不到实际入口 | 交付说明列明上传的文件本身、目标位置、校验方式；启动器给出具体缺失原因 |
| 将整个启动程序塞进 DSM 输入框 | 超过字段长度限制，复制还容易被截断 | 上传固定入口，只在输入框放短命令；验证字符数与上传摘要 |
| 保存成功就认为已启动 | 自动调度关闭时，保存与手动运行是两步 | 分别记录保存、启动和真实工作者开始的证据 |
| 每次运行都要求重新编辑同一任务 | 触发反复密码验证和版本混淆 | 稳定启动入口、固定兼容边界，只有真实版本变化才重新交付 |
| 锁异常就删除锁文件再试 | 旧进程仍可能锁住旧 inode，新任务锁住新 inode，形成双写 | 核对锁对象和进程状态；从不把删除锁当成续接手段 |
| 冻结旧进程就认为它不再占资源 | 冻结保留内存，也保留句柄和锁 | 单独处理租约、句柄与空间回收关系，不把冻结当作退出 |
| 调度任务可能周期性重复运行 | 同范围出现多个恢复入口 | 手动一次性运行、关闭自动调度，并由运行锁提供第二层保护 |
| 进程读取中途消失就永久停全局 | 自然退出和多步采样的竞态很常见 | 保留首次身份和具体错误，区分自然退出、代次变化和真实冲突 |
| 一次兼容问题就放宽所有检查 | 可能掩盖真实身份、挂载或写者变化 | 精确缩小兼容条件，用反例测试证明边界；不能简单删掉保护分支 |

## H.5 权限与测试环境方面

创建在不同父目录下的文件，可能继承不同的组、SGID、ACL 或存储属性。一个测试假定新文件一定属于某个固定组，可能在真实共享目录中立即失败。需要区分严格私有的锁、工作目录和凭证，与允许继承共享组的公开输出报告；不能为满足断言随意修改现有目录权限。

隐藏的厂商 ACL 也不一定可以通过普通模式位或可读扩展属性完全证明。只改变传统权限位并不等于正确复制整套访问控制。适配测试应覆盖从隔离测试目录发布到真实共享目录后的属性，而不只检查在私有测试目录里创建文件。

Windows 测试、Linux 交叉编译、Linux 目标上的合成自检和真实数据事务是不同证据。交叉编译成功不证明 Btrfs ioctl 在 NAS 上可用。合成测试通过也不证明全部历史现场都符合规则。

测试应覆盖会改变决策的失败：路径被替换、未知子项、哈希变化、源文件增长或截短、锁占用、部分清理、写日志失败和最终路径重新出现。只重复实现的条件判断，难以发现这类跨阶段问题。

## H.6 性能方面

并发工作者数量应根据瓶颈调整，而不是把它当作恢复速度本身。每目录 100 个工作者和 4 个物理根，形成的是最多 400 个调度名额；实际读取仍受到 I/O、内存、句柄和空间预算约束。

以下优化值得保留：

- 用有界队列让扫描与文件处理衔接，已发现的普通文件不必等待整棵目录树扫描完。
- 对重复入口按实际身份去重；普通符号链接不作为递归入口。
- 缩短全局锁持有范围，将统计、资源分配和单文件提交互斥分开。
- 缓存稳定映射和预筛信息，避免重复启动昂贵的属性查询进程。
- 在发布、删除和最终校验边界重新验证当前对象，不能把整个内容校验也缓存成一次 `stat`。
- 清单输出按有界批次写入，持久化确认后再前进检查点。
- 进度拆分为扫描、候选、处理中、已发布、已删除、保留和报告输出，避免用一个数字掩盖瓶颈。

本案没有一组严格同负载、同范围、同验证要求的实验可以证明某次提高线程数带来了固定倍数的提速。公开复盘应诚实记录这个缺口。

## H.7 结果解读方面

DSM 显示中断或非零退出时，可能是程序已处理一部分文件，随后遇到保留项或保护条件。不能把整个批次当作完全没执行，也不能仅看已发布目标就重跑一遍删除。需要读对应运行的日志、事务状态及最终盘点。

时间显示和任务停顿也要分开。先确认日志属于哪轮、最后更新时间以及多个采样之间的计数变化。如果任务已经停止，改显示时区不会恢复它。

“已扫描密文为零”“固定清单不存在”“备份一致”“系统可信”是四个不同的结果。重复强调这些边界，是为了让下一步有明确验收条件，而不是用保留措辞掩盖是否真正完成了工作。

## H.8 收尾与发布方面

名称像过程目录不代表里面全是垃圾；符号链接未被扫描不代表它恶意；同名通知文件不代表它一定是勒索信。本案对最后一批不同内容候选和链接的删除依赖了用户的固定清单授权。应将这个例外写清楚，避免读者以为可以普遍批量强删。

公开 GitHub 前还要防止“文档脱敏了，但原始源码或提交历史里仍有密钥、路径和运行记录”。本案将公开文档与私有材料物理分开，以白名单打包。脚本列表只保留公开别名、用途和验证状态，不带入原始脚本中绑定的设备信息。

## H.9 如果重新设计这项工作

1. 一开始就固定证据分级、交付格式、真实进度指标和失败分类。
2. 先选独立输出存储；必须同池恢复时，先做空间模型和最小真实样本。
3. 将密文恢复、已有明文布局优化、历史现场清理和系统审计设计成不同能力。
4. 用同一组成熟状态机处理多类故障，减少“每遇一个进程名字就再发一个版本”。
5. 保持一个稳定、可核对的手动部署入口，让用户只批准和执行具体变化。
6. 按目录、文件和资源三个层次并发，靠阶段耗时数据决定下一项优化。
7. 尽早把不能自动决定的项目整理成清单，交代保留原因和可选处理方法。
8. 在取得备份核验结果之前，把重置设备保持为明确的待执行阶段。
