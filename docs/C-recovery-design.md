# C．恢复原理与逐文件设计

本案例处理的是 NAS-A 上已定位的加密文件及一部分早期恢复遗留对象。示例中，`/VOL/A/a.enc` 是密文候选，`/VOL/A/a` 是对应的明文目标，`T` 是单个事务的过程目录。`.enc` 仅作示意。以下记录描述经审核的恢复入口支持的文件变体、证据和安全边界。

## 密钥材料能解决什么

材料获取的现场条件、早期证据及脱敏代码示例见 [K．密钥获取](K-memory-key-recovery.md)。其中明确区分已复得记录和本次重建示例。

批次密钥材料已经在事件处置中获得。恢复前先在副本上把密钥与当前样本绑定，优先找来源独立的原文件、备份或既有可信摘要。样本应覆盖实际加密区间，并验证整个文件。很小或没有实际加密字节的样本，即使一致也无法提供充分的密钥见证。来源不明的同名文件可以参加比对，可信度取决于它是否确实来自独立记录。

实现从文件末尾读取固定长度的尾部，检查实际文件大小、尾部声明的原始大小、支持的算法与模式，以及保留字段。尾部声明的原始大小必须恰好等于实际总长度减去尾部长度。对于该案例支持的变体，用批次材料进行 AES-256-CBC 解封装，取得每文件密钥和 nonce。解出的两份 nonce 必须相同。这个检查能拒绝许多错误密钥或不同批次的文件，文件本身仍缺少可用来验证历史原文的密码学认证标签。

载荷使用 ChaCha8。已实现的布局包括全量加密、仅波及文件开头和多个区间的间隔加密。解密器按尾部模式和已识别的参数计算区间，检查范围有序、互不重叠且在原始大小内，然后只在对应区间异或密钥流。计数器跨加密区间延续，未加密间隙原样保留，也无需消耗密钥流。发布后的明文长度精确等于尾部声明的原始长度，附加尾部留在原始密文中直至密文退出事务。不同版本的区间布局、计数规则或尾部长度必须独立确认。扩展名只能找候选，尾部解析成功只能提供格式与批次证据。截断、未识别模式、密钥疑似不匹配或读取错误进入保留清单。

部分实现还提供有限的结构见证。选定大小内的 PNG、JPEG 或 ZIP 容器要能完成图像解码，或读完归档内的各条目并校验大小与 CRC。归档检查还要求存在覆盖已加密载荷的条目。这样的验证比只检查文件头更有信息量，仍弱于独立原件的全文件匹配。最终授权入口会重新核验已有的内容见证后才进入使用密文作为来源的恢复流程。密钥及由此派生的每文件材料留在私有环境中。

## 密文仍然存在时

当 `a.enc` 能绑定到授权范围、当前文件身份和受支持的尾部，先记录其全文件 SHA-256、大小、inode、链接数、所有者、权限、时间及可读取属性，并确认 `a` 是否存在。要以固定目录句柄打开普通文件，拒绝通过符号链接引用数据，以及在锁定与提交之间发生的 inode 替换、多硬链接或越界挂载。不存在 `a` 时，在同一文件系统的私有过程目录 `T` 内创建候选，写入完成并验证后以禁止覆盖的方式发布。此间若有其他程序创建 `a`，发布失败并保留现场。

存在同名明文时，先读取它的完整摘要并与密文逐字节往返比对。若已验证一致，严格存储模式可根据当前共享情况和属性选择保留现有 inode，再走单独的密文清理步骤。历史上也有先做受控替换、再删除密文的模式。若同名明文与密文的还原结果有差异，常规处理是保留两者。最终优先任务中有一项单独审核的授权政策，允许固定范围内经验证的已知批次密文作为恢复来源。该分支要记录现有明文的全量摘要，将其作为旧明文受保护地备份进 `T`，验证候选并原子发布。标准的发布和持久化验证通过后，才按各自的事务顺序清理旧明文备份和原始密文。仅凭出现了同名密文，无法证明当前明文是坏件。涉及后来编辑过的文件时，尤其需要独立来源判断。

### 全流往返校验的边界

往返校验同时读取明文与密文。加密区间将候选明文按同一算法转回密文并逐段比较，非加密间隙直接比较。校验覆盖真实尾部、两端精确 EOF 和完整的明文、密文流，分别计算 SHA-256。密文摘要须和准备阶段读到的值一致，有绑定的历史证据时两端摘要还须符合那份证据。旧明文、历史摘要和已验证的独立副本各有不同的证据来源，应在记录中标明。

这一检查能发现短读、多余字节、补丁只写了一部分、间隙被改坏、内容在检查之间变化等问题。若候选完全由同一份密文及同一套可逆算法生成，同一错误密钥也可能产生能转回原密文的输出。全流往返本身证明的是当前文件对在指定变换下的一致性。要证明还原结果确是事件前版本，仍依赖独立原件或可信的历史摘要。校验过程中产生的 SHA-256 可以固定当前读取的字节，无法为来源补签历史凭证。

## 密文已经不存在时的存储布局重建

早期恢复有可能恢复了文件内容，却用独立复制分配了大量存储，使 `a` 内容正确但占用偏高。若 `a.enc` 已经不存在，此处无法再拿密文重做往返。历史重建分支要求有经过审核、能绑定 `a` 及其供体 `b` 的历史证据，且两端此刻的全文件 SHA-256 均匹配可信明文摘要。还要确认授权范围、大小、当前 inode、文件系统和单链接状态，避免供体与目标实为同一个 inode、指向其他卷，或与一个未解决的旧事务并存。两份内容相同但都没有独立历史证据，只能说明当前两份内容一致。

这一分支在 `T` 内从供体克隆候选，再以现有明文为字节基准逐块比较，只写有差异的区块，并截到精确目标长度。由于本案例的历史重建入口要求供体和现有明文原本已有相同的全量摘要，正常成功时预期没有数据差异。代码会再检查候选全文件内容、保留目标需继承的属性，并在严格策略下确认共享区块存在且独占字节确实下降。供体本身只读，旧明文经受控替换及持久化验证后才可退出事务。找不到匹配供体、旧明文摘要已变或测不到预期存储收益，就保持原件。这项独立能力须另行授权。最终优先任务的遍历以仍有密文的文件为恢复对象，不能据此声称所有先前恢复的明文都完成了物理空间重建。

## Btrfs 共享空间的条件

共享克隆和写时复制的通用语义可查 [Linux 接口手册](https://man7.org/linux/man-pages/man2/ioctl_ficlonerange.2.html)，去重涉及的存储属性兼容条件可查 [Btrfs 文档](https://btrfs.readthedocs.io/en/latest/Deduplication.html)。以下具体策略和测量结果来自本案例实现与记录，并不由这些通用资料替代验证。

reflink 给候选创建独立 inode，在起始状态引用与原文件相同的数据区块。它与把两个名字指向同一 inode 的硬链接有不同语义。写入共享区块会引起写时复制（CoW），未改区间可继续共享。采用密文分支时，仅重写已加密范围，尾部截短也可能触及最后一个物理区块。全量加密文件几乎没有可保留的未加密载荷。明文重建时若已有单独验证的同内容供体，则可能让新目标重新共享供体的数据区块。若密文最终删除且这些区块无其他引用，原密文的独占分配才有机会释放。快照、其他克隆和尚未关闭的文件描述符都会影响实际回收。

严格模式要求 Linux 的 `FICLONE` 成功，且在候选仍为空且私有时读取和准备 CoW、NOCOW 或压缩等存储属性，再读回确认。继承的 NOCOW 与压缩可能冲突，严格实现对已审核的组合才做分步调整。内核决定该文件对能否克隆，失败时保留源。以内容恢复为优先的后期策略也先尝试 reflink，在逐文件预留足够空间的前提下，只对明确的能力或兼容性错误采用有预算上限的独立复制，错误和属性差异写入记录。它读取文件已分配块数作为参考，此计数不能区分独占和共享字节，也不能证明得到了预期的空间收益。

空间预算须同时覆盖新候选、密文和旧明文存活时的峰值，以及块对齐、CoW、目录与日志的额外开销。小范围试跑可对比逻辑长度、已分配字节、Btrfs 独占/共享度量和文件关闭后的可用空间。预留空间只是控制当前并发任务的预算，卷上其他工作、快照和文件系统元数据开销仍会影响最终可写空间。这个流程无法承诺零额外空间。

### 早期恢复为何使空间吃紧

早期转换路径逐段读原文件，但新输出对加密区间和未加密间隙都执行普通写入。恢复文件与密文同时存在时，同一份内容会独立分配两次，原本能保持共享的大量未加密区间也会重写。早期清理还曾等一个目录的一批工作结束再删除密文，放大了在途峰值。检查发现该设备上有 CoW 密文位于 NOCOW 父目录下，直接创建的新文件会继承 NOCOW，加上原先走独立写入，导致已验证正确的明文仍可能持有大量独占分配。严格修复方案因此先让空的私有候选与密文满足克隆兼容性，再只改写实际加密字节。

一个实际单文件试点把一份约 57 MB 的密集分配明文换成经过完整验证的共享候选。旧明文约 57 MB 的独占分配，对照候选当时的独占测量为 0，且试点保留了密文和一份用于验证的重建样本。提交后卷可用空间没有马上增加，稍后的观察相对提交前约增加 57 MB。这与旧分配延迟释放一致，卷级采样无法把每个变化都归给这一件文件。历史核对还在已验证文件的完整摘要中发现约 26 GB 的整文件重复候选上界，当时尚未确认现存供体、可共享程度或实际可回收字节。由这些证据可以解释为何旧恢复会额外占用空间，无法逐项归因约 2 TB 的空闲下降，也无法预报能找回多少。同内容独立复制、单纯变更 NOCOW，或克隆一份自己随后会移除的独占文件，都无法自动复原原先的共享关系。

## 删除前必须完成的事务

| 阶段 | 要留下的证据 |
| --- | --- |
| 准备 | 锁定目录、源、目标与必要的旧文件句柄，核对范围、挂载、链接数、属性、当前身份及完整源内容，预留空间并创建私有过程目录。 |
| 候选就绪 | 落盘事务计划与候选，记录身份、完整摘要、目标出现/不存在的条件、要删除的准确对象。所有者、权限、时间、扩展属性与 ACL 按当前策略核对。 |
| 发布 | 先同步发布意图，再做提交前的新鲜验证。新目标用拒绝覆盖的原子发布。已授权替换先固定旧件及其备份链接，再用目录内原子重命名发布，随后同步目录。 |
| 清理 | 同步删除意图后，重新验证已发布目标的完整内容、源和备份身份、目录项、链接数与引用状态。只移除计划中已绑定的条目，同步目录、关闭旧描述符，测量空间，再记录完成。 |
| 保留 | 当内容不符、路径变更、链接异常、空间不足、同步失败或证据不全时，保留当时仍存在的对象及事务记录。新一轮按当前状态复核，遇到未知过程目录可另行只读核验。 |

属性处理有阶段性区别。早期严格模式要求按已审核的所有者、权限、时间与可读扩展属性规则复制并复验，对无法证明的 ACL 或未知存储状态保留。后期内容优先模式对明确不支持的属性能力、不能精确证明的厂商 ACL、读回差异或访问时间漂移记录警告，并继续完整内容与身份校验。它无法由此证明所有原有 ACL 或平台扩展属性都被完整还原。涉及业务权限时，需在新环境用相应身份及应用实测可读写情况，检查私有文件和共享目录的可见性。

中断点会决定保留哪些对象。发布后可能同时看到明文、密文和 `T`，清理中断后也可能只剩明文、旧件或日志的一部分。不能用旧日志单行、进程退出或目标同名作为重复删除的条件。恢复记录应能把“已写候选”“已发布”“已同步删除及关闭”和“待复核”分开。需要清除过程目录时，先证明目录身份、当前内容和必要的历史关系，将证据独立归档，再按批准的对象顺序逐项处理。未知载荷可能是唯一剩余副本，按未决项保留。
